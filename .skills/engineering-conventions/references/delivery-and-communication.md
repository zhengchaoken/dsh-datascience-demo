# 交付与沟通范式

## 适用场景

用户在推进工程任务、要求产出代码或文档、指出上一次结果有问题时，适用本文件。

## 输出形态

- 要代码就输出**完整可运行的文件内容**，不要只给片段、示例、伪代码或「你可以这样写」。
- 要方案就输出**结论 + 可执行步骤**，不要先铺垫背景再慢慢收敛。
- 不提问、不复述用户需求、不解释「我准备怎么做」，直接做。
- 中间过程只报**决策点、阻塞点、状态变化**，不报「正在思考」「马上开始」。
- 思考过程用中文并展开，不折叠。

## 文件产出判定

产出前先问自己：这个文件是非有不可吗。

| 情况 | 做法 |
|---|---|
| 已有同类文件 | 编辑它，不新建 |
| 只是临时验证 | 放临时目录或直接跑命令，不落在项目主目录 |
| 用户没要求文档 | 不创建 README、总结、说明文档 |
| 用户明确要交付物 | 才创建，并放在用户指定或工作区约定位置 |

用户要求「整理项目 / 删无用文件」时，先列清单（候选、理由、影响），再执行；文档与入口文件必须先确认。

## 对外界面文案准则

界面是给最终用户看的，不是给开发看的。

- 不出现「本页用于演示」「以下内容为示例」「由 AI 生成」这类说明。
- 不出现内部代号、分支名、临时变量名、TODO、校对标记。
- 不出现「完善了」「优化了」「修复了」这类开发过程表述。
- 术语统一：同一个概念全站一个叫法，不混用中英。
- 内容不一致时，在对话框里说明差异与原因，界面只呈现最终一致版本。

## 完成的标准

一句「已完成」必须同时满足：

1. 类型检查通过（如 `npm run typecheck`）。
2. 构建通过（如 `npm run build` / `build:web`）。
3. 有运行时的功能，做过一次真实请求或一次真实启动验证。
4. 已知偏差如实说明（没验证的部分要讲清楚，不能默认没问题）。

只跑了其中一步就声称全部通过，属于返工点。

## 常见返工点

- 用户说「不要动代码」，却改了文件。评估类请求只输出判断与方法。
- 用户说「输出到某个文件」，却只在对话里贴内容。
- 用户指出上轮问题，答复里重新解释一遍背景，而不是直接修。
- 把「编译通过」等同于「功能正确」。
- 界面里残留设计说明、字段注释式的解释文字。
