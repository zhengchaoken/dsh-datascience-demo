# 数据探查：建模前的一次完整体检

> **一句话**：探查不产出模型，产出的是**“这份数据能不能用、哪里不能用、用之前要改什么”**的判断。
> 数据源为 `../ecommerce/ecommerce.db`（九张表），方法论总览见 [../README.md](../README.md)。

---

## 1. 为什么先探查

建模踩的坑，绝大多数不是模型不够强，而是数据本身有问题：

- 主键重复导致 JOIN 后数据翻倍，指标凭空放大；
- 缺失值不是“没有”，而是业务状态（未支付、未发货），当成 0 填就错了；
- 金额勾稽不上，GMV 口径自相矛盾；
- 长尾分布按均值做预算，严重低估。

探查把这些问题在**动手之前**暴露出来，给出可复现的证据。

## 2. 探查的五个维度

| 维度 | 要回答的问题 | 典型产出 |
|---|---|---|
| 结构 | 有哪些表、多少行、主键是什么、表怎么关联 | 数据字典、表规模、候选主键 |
| 完整性 | 哪些字段缺失、缺失是否有业务含义 | 缺失率矩阵、缺失语义 |
| 一致性 | 外键、金额勾稽、时间链是否成立 | 跨表检查清单 |
| 分布 | 数值是否长尾、分类是否失衡、时间是否连续 | 分布图、异常值清单 |
| 就绪度 | 能否直接建模、需要哪些清洗与特征工程 | 建模就绪度结论 |

## 3. 电商数据集的探查结论

**规模。** 9 张表、162,276 行，时间跨度 532 天（2024-01-01 ~ 2025-06-15）。行为事件表体量最大（76,905 行），订单 19,669 行、明细 36,907 行是交易分析主表；主数据表保持小体量，符合维度表与事实表的典型比例。

**完整性。** 全库只有 5 个字段存在缺失，且**每一个缺失都有明确业务含义**：

| 字段 | 缺失率 | 业务含义 |
|---|---|---|
| `categories.parent_id` | 20.00% | 一级类目没有父节点，NULL 表示类目树根 |
| `orders.coupon_id` | 78.70% | 该订单未使用优惠券 |
| `orders.paid_at` | 2.48% | 订单尚未支付（待付款或已取消） |
| `orders.shipped_at` | 7.81% | 订单尚未发货 |
| `orders.delivered_at` | 12.09% | 订单尚未签收 |

结论：**不能把这些 NULL 当脏数据填掉**，应按状态机解释。

**一致性。** 11 项跨表检查中 10 项通过、1 项提示、0 项风险：

- 外键完整，九表可直接多表 JOIN；
- 订单金额勾稽（实付 = 明细小计 + 运费）0 单不一致；
- 优惠金额勾稽、支付覆盖、支付金额一致、评价归属与唯一性、优惠券门槛全部通过；
- **提示项**：3,840 单存在同一日内发货时刻早于支付时刻，日期粒度的时间链正确，“支付到发货时长”类指标应按日期为粒度；
- **行为闭环**：57.21% 的浏览 / 加购事件能在 7 天内对应到成交订单，其余为未转化行为，漏斗分母应取全部浏览事件。

**就绪度。** 主键唯一、外键完整、金额可勾稽，可直接做多表分析；数值字段存在少量**业务型异常**（批发大单、价格异常），这是 L2 异常检测的靶子，不应直接剔除。

## 5. 脚本

`data_profiling_report.py` 可对**任意 SQLite 库**复跑，不绑定电商数据集：

```powershell
# 默认探查 ecommerce.db
python src/data/profiling/data_profiling_report.py

# 指定库与表
python src/data/profiling/data_profiling_report.py --db path/to.db --tables orders,payments
```

脚本以只读方式连接（`mode=ro`），不会修改源数据。完整环境与执行顺序见 [../run.md](../run.md)。

## 6. 探查之后做什么

探查结论直接对应后续每一层的输入：

- 长尾分布 → L1 必须同时报告分位数；
- 业务型异常 → L2 做异常检测与解释，不剔除；
- 时间链与 532 天连续日粒度 → L3 时序建模的前提；
- 用户-商品隐式反馈可构造 → L4 推荐的基座；
- 缺失语义按状态机解释 → L5 持续学习中的批次分布差异要单独处理。
